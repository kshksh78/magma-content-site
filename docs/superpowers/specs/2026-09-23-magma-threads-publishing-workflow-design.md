# MAGMA Threads 콘텐츠 발행 워크플로 설계

- 상태: 설계 승인됨, 문서 검토 및 워크플로 등록 전
- 대상: BlueKiwi, `My Workspace`
- 목적: MAGMA의 공용 자료에 근거한 Threads 게시물을 후보화하고, 후보 선택과 외부 게시를 분리 승인한 뒤, 게시 결과와 중복 방지 정보를 반복 가능하게 보존한다.
- 범위: 텍스트 기반 Threads 게시물 한 건을 반복 단위로 처리한다. 콘텐츠 방향·브랜드 판단은 출처에 근거해 제안하고, 게시 전후의 외부 부작용은 명시적 사용자 승인에만 따른다.

## 설계 선택

세 접근을 검토했다.

1. 게시물 한 건마다 별도 실행: 단순하지만 매 게시마다 처음부터 재실행해야 한다.
2. 한 워크플로 안에서 게시 건별 반복(권장): 매 반복마다 자료 확인, 중복 점검, 후보 선택, 게시 승인, 게시 결과 기록을 수행한다. 후보 선택과 실제 게시 승인이 분리되어 실수 위험을 줄인다.
3. 후보 여러 건 일괄 게시: 효율적이지만 승인 경계와 중복·실패 처리가 흐려질 수 있어 초기 운영에 부적합하다.

따라서 2번을 선택한다. 한 번의 반복에서는 게시물을 최대 한 건만 외부에 발행한다. 다음 반복을 할지는 결과 기록 후 사용자가 결정한다.

## 워크플로 단계

1. 공용 컨텍스트와 정본 상태 확인 — action
2. 중복 확인 및 게시 후보 3개 작성 — action
3. 후보 선택 — gate
4. 선택 후보 최종화 및 사실·보이스 검수 — action
5. 실제 게시 승인 — gate
6. Threads 게시 및 결과 기록 — action
7. 다음 게시물 진행 여부 — loop, 1단계로 복귀

## 단계별 계약

### 1. 공용 컨텍스트와 정본 상태 확인

실행 시 현재 프로젝트 `~/.hermes/workspace/magma-content-site`와 `~/.hermes/company/README.md`부터 읽는다. README 링크를 따라 회사 컴퍼니북의 브랜드 전략, 브랜드 보이스, 시장조사, 가격 포지셔닝, VI, 런칭 문서와 공용 프로젝트의 브랜드 자료를 확인한다. 날짜만으로 정본을 정하지 않는다. 각 문서의 명시적 상태, 버전, 승인 여부, 담당 영역을 기록하고, 동일 주제에 충돌이 있으면 권한이 명시된 도메인 정본과 최신 승인본을 우선한다. 프로젝트 `DESIGN.md`는 문서 자체가 공식 디자인 정본이라고 선언하므로 VI 충돌 시 별도 승인된 최신 자료가 발견되지 않는 한 이를 우선한다. 런칭 패키지의 “최종 배포본” 표기만으로 대표 승인이나 고객 검증이 끝난 것으로 추정하지 않는다.

### 2. 중복 확인 및 게시 후보 3개 작성

프로젝트 기존 게시물과 `content/posts/.threads-published.jsonl`을 확인한다. 이력 파일이 없으면 빈 기록으로 취급하되, 기존 게시물도 훑어 제목·본문·주제 중복을 검사한다. 이력은 게시 완료 뒤에만 추가하며 기존 줄을 수정·삭제하지 않는다. 각 후보는 서로 다른 주제 각도와 메시지를 가져야 하며, 본문 초안, 의도, 근거 문서·절, 근거 상태(Data/Opinion/Assumption/Decision 또는 이에 준하는 문서 표기), 미확정 표현 여부, 기존 게시물과의 차이를 포함한다. 확인 가능한 사실과 제안·가설을 섞어 단정하지 않는다. 중복 후보는 다시 생성해 최종 3개를 제시한다.

### 3. 후보 선택 gate

후보 3개의 본문과 사용 근거를 한국어로 비교해 보여주고 정확히 하나를 선택하게 한다. `bk-options`를 사용하며 각 선택에는 후보 번호와 짧은 식별 문구를 둔다. 추가 선택은 “수정 요청”과 “이번 실행 중단”이다. 선택 외에 전역 `comment`와 수정 요청용 메모를 받을 수 있도록 `bk-textarea`를 제공한다. 수정 요청이 있으면 이를 4단계에 전달하고 사용자가 선택하지 않은 다른 후보를 임의로 게시하지 않는다. 선택이 없거나 중단이면 이후 단계로 자동 진행하지 않는다.

### 4. 최종화 및 검수

선택된 후보만 게시 가능한 최종 텍스트로 정리한다. 근거 없는 품질·가격·내구성·고객 반응 주장은 삭제하거나 미확정으로 표시하고, 브랜드 보이스의 과장·나이 평가·느낌표 남발 금지를 확인한다. Threads의 현재 게시 요건과 길이 제한은 실행 시 공식 문서 또는 등록된 게시 연동의 최신 명세로 확인하며 기억에 의존한 제한값을 적용하지 않는다. 게시 텍스트, 적용 근거, 최종 글자 수와 검수 결과를 출력한다. 미해결 사실 충돌, 공개 금지 정보, 계정 불일치가 있으면 게시 승인 단계로 넘기지 말고 확인 필요 상태로 종료한다.

### 5. 실제 게시 승인 gate

최종 게시 텍스트와 대상 Threads 계정을 그대로 제시하고, 별도의 명시적 게시 승인을 받는다. `bk-options` 선택지는 “게시 승인”, “수정 후 다시 검토”, “취소”다. “수정 후 다시 검토”는 메모를 필수로 받으며, 수정 후에는 4단계 검수와 이 gate를 다시 거친다. “게시 승인” 이외의 응답으로는 외부 API 호출을 하지 않는다. 승인 기록과 선택한 최종 텍스트 해시를 결과에 남긴다.

### 6. Threads 게시 및 결과 기록

사용자 승인을 받은 텍스트만, 승인된 MAGMA Threads 계정에 연결된 자격 증명으로 한 번 전송한다. 실행 전 자격 증명과 계정 식별을 확인한다. 자격 증명이 없거나 계정을 검증할 수 없으면 비밀값을 대화에 요구하지 말고 중단한다. API 응답이 성공을 명확히 확인한 경우에만 `content/posts/.threads-published.jsonl`에 JSONL 한 줄을 append한다. 각 레코드에는 UTC 게시 시각, Threads post ID, permalink, 정규화 본문 SHA-256, 원문 본문, 후보 ID, 근거 문서 경로·섹션, 계정 식별자를 기록한다. 토큰과 비밀값은 기록하지 않는다. 결과가 불명확하거나 타임아웃이면 자동 재시도하지 않고 `pending_verification`을 별도로 남겨 중복 게시를 막는다. 실제 게시 성공과 이력 기록 성공을 각각 검증하고 구분해 보고한다.

### 7. 다음 게시물 반복

게시 결과와 기록 상태를 사용자에게 요약한 뒤 다음 게시물을 진행할지 묻는다. 계속이면 1단계로 돌아가 최신 문서와 이력을 다시 읽는다. 중단이면 완료 상태와 이번 실행의 게시 건수·실패/확인 대기 건수를 요약한다. 한 반복에서 게시 승인되지 않았거나 게시 결과를 검증하지 못한 건을 성공 건수로 세지 않는다.

## 실패·안전 경계

- 현재 BlueKiwi 자격 증명 목록은 비어 있다. 게시 노드는 Threads 연동 자격 증명이 안전한 경로로 생성·연결되기 전까지 실패-안전(fail closed) 상태여야 한다. 이 설계 승인만으로 API 자격 증명을 만들거나 외부 게시를 수행하지 않는다.
- 후보 선택과 실제 게시 승인은 각각 독립 gate다. 한 번의 승인을 두 단계에 재사용하지 않는다.
- HTTP/API 실패·불확실한 응답에서는 재전송하지 않는다. 게시물 존재 여부 확인 전에는 동일 해시 재게시를 금지한다.
- 이력은 append-only다. 이전 이력이나 기존 게시 파일을 덮어쓰지 않는다.
- 브랜드 문서 간 미해결 충돌은 사용 근거와 함께 노출하고, 확인되지 않은 내용은 게시 사실처럼 표현하지 않는다.
- 외부 게시 성공, 이력 파일 기록 성공, 두 결과를 검증한 시각을 분리해 보고한다.

## 완료 기준

- BlueKiwi 워크플로는 7단계와 지정한 1단계 복귀 루프를 가진다.
- 각 단계 지시는 역할/맥락, 최소 2개의 수행 방법, 정확한 산출물, 검증 방법을 포함한다. loop 지시는 명시적 종료 조건을 마지막에 둔다.
- 모든 단계 지시는 최소 80단어이며, 한국어로 작성한다.
- 두 개의 승인 gate, 중복 방지, append-only 게시 기록, credential fail-closed 경계가 존재한다.
- 생성 응답의 `node_verification.mismatch`가 false임을 확인하고, 등록된 워크플로를 다시 조회해 7개 단계와 루프 구성을 확인한다.
