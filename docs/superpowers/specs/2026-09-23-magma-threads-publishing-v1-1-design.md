# MAGMA Threads 콘텐츠 발행 v1.1 설계

- 상태: 사용자 설계 승인 완료 / BlueKiwi 새 버전 생성 전
- 기준일: 2026-09-23
- 기준 워크플로: `MAGMA Threads 콘텐츠 발행` v1.0, workflow ID 5
- 목표 버전: v1.1
- 저장 위치: BlueKiwi My Workspace
- 범위: 기존 후보 작성·승인·게시·내부 기록·반복 구조를 유지하면서 정본 우선순위를 명시하고, 후보 생성 전 정본/승인 상태 gate를 추가하며, 내부 증거와 게시 본문을 분리한다.

## 배경 및 현재 상태

기존 v1.0은 7단계다. 정본 감사, 중복 점검 및 후보 3개 작성, 후보 선택 gate, 최종화·검수, 실제 게시 승인 gate, 게시·결과 기록, 다음 게시 반복을 수행한다. 과거 실행 task는 없으므로 반영할 `feedback_data`는 확인되지 않았다.

회사 README는 브랜드 전략, 시장조사, 가격, 보이스, VI와 런칭 자료의 인덱스다. 현재 README가 가리키는 최종 런칭 패키지는 배포용 최종본으로 표기되어 있으나 문서 본문에는 대표 승인·고객 검증 전이라고 적혀 있다. 최신 날짜나 `final` 파일명만으로 승인이 끝났다고 추정할 수 없다. 또한 프로젝트 DESIGN.md와 회사 디자인 자료 사이에는 시각 기준 차이가 있으므로 실행 시 명시적 정본 상태와 승인 여부를 대조해야 한다.

## 설계 결정

1. v1.0을 수정하지 않고 v1.1을 같은 워크플로 family에 새 버전으로 생성한다.
2. 기존 정본 감사 직후이자 중복 점검·후보 작성 전에 `정본·승인 상태 확인` gate를 추가한다.
3. BlueKiwi의 gate는 항상 사용자 확인을 기다린다. 자료에 충돌이 없어도 gate에서 “이 기준으로 계속” 확인을 받는다. 충돌 또는 승인 상태 불명확이 발견되면 후보를 만들기 전에 쟁점별 문서 상태와 선택 가능한 정본을 제시하고, 모든 쟁점이 명시적으로 해소될 때만 계속한다. 하나라도 미해결이면 후보 작성으로 진행하지 않는다.
4. 회사 README가 지정한 현재 문서 인덱스와 각 문서의 명시적 상태, 담당 도메인, 승인 여부를 확인한다. README가 가리키는 최신 자료 중 명시적으로 확정·대표 승인된 내용을 우선하며, 최신 승인 launch package를 오래된 초안보다 우선한다. 날짜나 `final` 표기만으로 승인 사실을 추론하지 않는다. 상태가 불명확하거나 자료가 충돌하면 새 gate에서 사용자에게 결정을 요청한다.
5. 후보 3개 생성, 기존 게시물 및 JSONL 중복 검사, 후보 선택 승인과 실제 게시 승인, 한 건씩 반복하는 구조는 유지한다.
6. 검토 UI와 내부 JSONL에는 근거 파일 경로·절·상태를 보관한다. 게시용 `public_text`는 내부 증거 데이터와 별도 필드로 유지하며, Threads API에는 `public_text`만 전송한다. 후보 검토 gate에만 근거 파일 정보를 표시하고, 실제 게시 승인 화면은 최종 공개 본문과 대상 계정을 제시하되 내부 근거 파일 정보를 포함하지 않는다.
7. 최종 게시 본문에 파일 경로, 파일명, 내부 인용·링크, 내부 상태 라벨, 후보 ID, 검토 메모 등 내부 메타데이터가 섞이면 게시를 차단하고 본문을 수정·재검수한다.
8. 기존 fail-closed 자격 증명 검사, 실제 게시의 별도 승인, 불확실한 응답의 자동 재시도 금지, 성공 확인 뒤에만 append-only ledger에 기록하는 원칙을 유지한다. 워크플로 개선만으로 credential을 생성하거나 실제 게시하지 않는다.

## v1.1 단계 구성

1. **공용 컨텍스트와 정본 상태 확인** — action. 프로젝트와 회사 README를 읽고 관련 최신 문서의 상태·버전·도메인 정본·승인 여부를 수집한다. 사실/의견/가정/결정을 구분하고, `source_audit` 결과에 정본 우선순위, conflict 목록, approval ambiguity 목록, 확인 근거를 구조화한다.
2. **정본·승인 상태 확인** — gate. 앞 단계의 `source_audit`를 읽는다. 문제 없음 상태도 사용자에게 보여주고 계속을 확인한다. 충돌/불명확 항목마다 관련 문서, 상태, 상충 주장 및 선택지를 제공한다. 모든 항목에 명시적 결정을 받지 못하면 종료·보류한다. 이 gate 승인 전에는 후보를 만들지 않는다.
3. **중복 확인 및 게시 후보 3개 작성** — action. 사용자가 승인한 정본 처리 결과와 이전 발행물을 사용해 기존 JSONL/게시물을 검사하고 서로 다른 세 후보를 만든다. 각 후보는 `public_text`와 내부 전용 `evidence`를 분리한다.
4. **후보 선택** — gate. 세 후보 각각의 `public_text`, 의도, 내부 근거 파일·절·상태 및 중복 비교 정보를 검토 화면에 제시한다. 선택·수정 요청·중단을 구분하고 수정 메모를 보존한다. 이 승인은 게시 승인이 아니다.
5. **최종화 및 사실·보이스 검수** — action. 선택 후보의 공개 텍스트만 다듬고, 주장을 승인된 근거와 대조한다. 파일 경로/파일명/인용/내부 근거 metadata 노출 검사를 수행한다. 통과하지 못하면 게시 승인으로 보내지 않는다.
6. **실제 게시 승인** — gate. 정확한 `public_text`와 검증된 대상 계정을 제시한다. 내부 근거 파일은 이 공개 본문/승인 화면에 넣지 않는다. 게시 승인, 수정 후 재검토, 취소를 구분하며, 명시적 게시 승인만 다음 단계로 진행한다.
7. **Threads 게시 및 결과 기록** — action. 유효한 계정 일치 credential과 명시적 승인 없이는 fail-closed로 중단한다. Threads 요청 payload는 `public_text`만 담는다. 명확한 성공 응답 후에만 기존 `content/posts/.threads-published.jsonl`에 append-only로 기록하며, 내부 증거 경로를 ledger에 유지한다. 불확실한 응답은 자동 재시도하지 않고 확인 대기로 남긴다.
8. **다음 게시물 반복** — loop, `loop_back_to=1`. 게시/기록 결과를 요약하고 계속이면 새 자료 감사로 돌아간다. 멈춤이면 실행을 종료한다. 종료 조건을 loop 지시의 마지막 줄에 적는다.

## 오류·안전 처리

- 회사 README를 읽을 수 없거나 연결 문서를 찾지 못하면 상태를 추정하지 말고 확인 필요로 표시한다.
- 승인/확정 여부가 문서에 없거나 상충하면 `approval_ambiguity`로 기록하고 2단계 gate 전에 후보 생성 금지.
- gate 응답이 누락되거나 모든 충돌이 해소되지 않으면 후보 생성 또는 게시를 진행하지 않는다.
- 공개 본문과 내부 증거의 데이터 경계를 유지한다. 본문에 내부 파일 메타데이터가 있으면 전송을 막는다.
- 사용자 요청과 무관하게 v1.0을 덮어쓰거나 archive하지 않는다. v1.1 생성 결과에 대한 서버 응답 및 실제 version family 상태를 확인한다.

## 완료 기준

- 같은 workflow family에 8개 노드를 포함한 새 v1.1이 존재하고 기존 v1.0은 보존된다.
- 새 gate는 정본 감사 다음, 후보 작성 전에 위치한다. 깨끗한 감사라도 gate에서 사용자 확인을 받는다.
- 정본 우선순위는 명시적 승인/확정 상태를 기준으로 하고, 날짜와 `final` 표기만으로 승인 상태를 추론하지 않는다.
- 후보 3개 작성 흐름, 두 개의 별도 승인 gate, 중복 방지 기록과 1단계 복귀 loop를 유지한다.
- 후보 검토 화면/내부 기록에는 근거를 보존하지만 실제 Threads 요청에는 공개 본문만 포함한다.
- 기존 credential fail-closed, 성공 후 append-only record, 불확실할 때 재시도 금지를 유지한다.
- 새 버전 등록 후 서버에서 실제 version, node IDs/orders/types, gate 위치, loop target, instruction lengths/content, credential binding absence를 다시 읽어 검증한다.
